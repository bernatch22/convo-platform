05 · Entregable 4 — diseño de tools y contratos

El contrato se lee dos veces: una la máquina y otra el modelo

Ninguna función es una tool hasta que declara qué le hace al mundo. El ToolSpec es lo que lee la plataforma; el docstring, lo que lee el modelo. Descrita sólo en el prompt, el guard se queda sin nada que comprobar: no hay dónde escribir «esto es irreversible». 

@dataclass(frozen=True)
class ToolSpec:
    name: str
    side_effect: SideEffect          # read | write | irreversible
    idempotency_key: str | None = None
    pii_scope: frozenset[str] = field(default_factory=frozenset)
    timeout_s: float = 8.0
    compensation: str | None = None
    result_summary: Callable[[Any], str] | None = None
    infrastructure: bool = False

BOOK_SLOT = ToolSpec(
    name="book_slot",
    side_effect=SideEffect.IRREVERSIBLE,      # exige token de confirmación
    idempotency_key="slot_id",                # un reintento no reserva dos veces
    pii_scope=frozenset({"phone", "patient"}),
    compensation="cancel_slot",               # el deshacer, declarado
    timeout_s=8.0,
    result_summary=summarise_change,          # la única línea que el log guarda
)
01
El efecto decide, no el nombre Gobierna confirmación, reintentos y registro. El tablero cuenta transacciones leyendo irreversible del log, nunca una lista de nombres.
02
El fallo tiene dos audiencias ToolError es la única que el modelo lee, y su mensaje es una frase que el llamante podría oír. Lo demás se traduce; la causa real va al log.
03
El log guarda la forma, no el resultado tool.result registra list[3], jamás la fila de la agenda. result_summary es opcional y pasa por la máscara de PII.
04
Un contrato, tres ejecutores ToolExecutor es un Protocol: local hoy, en el proceso del cliente mañana. Por encima de esa línea no cambia nada.
